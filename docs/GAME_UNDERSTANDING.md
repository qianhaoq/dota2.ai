# 教练怎样真正"看懂"一局 Dota 2

这份文档讲的是：教练对一局比赛的理解卡在哪一层，怎样从零补到一，以及每一步怎么衡量做没做到。第一步是 `fight_report` 和 `game_state` 两个工具，以及配套的校准脚本，已经实现。

## 1. 理解一局比赛分几层

一个好教练看录像，脑子里大致是这样一叠：

| 层 | 问的是什么 | 现在有没有 |
|---|---|---|
| 规则 | 这个技能、这件装备在这个版本里做什么 | 有：Valve 数据、逐版本快照、补丁原文（`patchData.js`、`hero_abilities`、`build_check`） |
| 事件 | 发生了什么：谁死了、放了什么、拆了什么、出了什么 | 有：`match_overview`、`death_context`、`ability_audit`、`fight_timeline`、`item_timeline` |
| **局面** | 某一秒的比赛是什么样：谁在哪、在干嘛、什么技能和装备好了 | **没有**。各工具各自临时算位置（`nearby`、`region`），没有一个工具直接回答"那一刻大家在哪" |
| **因果** | 结果为什么是这样：这波团为什么输 | **靠模型猜**。工具只说死了谁，不说"3 打 4、我方核心在对面下路、没有 TP" |
| 判断 | 当时该怎么做 | 靠模型自带的 Dota 知识，这部分既不可靠，也常停留在旧版本 |
| **衡量** | 上面这些做得对不对 | **第一级已实现**：确定性探针（`scripts/probe-chat.mjs`），对话 agent 读工具的准确率：一步的题 en 99%、zh 100%，两步的题 en 97%、zh 98%。#164 的标注语料还是 0 局 |

问题主要出在中间两层。模型拿到的是一串事件，局面得它自己拼。人看录像第一眼看的是全图，模型第一眼看到的是一行死亡记录。拼不出局面，因果就只能编；因果靠编，判断再好也是空的。

## 2. 一个实验：直觉定义的局面特征会骗人

线上已经解析过的 32 局里共有 321 场分出胜负的团战（一方死得更少）。我想看看"团战前的局面"能不能解释胜负。

第一版用直觉定义"在场"：团战开始时离死亡地点 3000 码以内。结果在场人数多的一方只赢了 **43%**，比抛硬币还差。原因是死掉的人天然就在死亡地点，这个定义系统性地把输家算成"人多"。

改用实测定义"参战"后，结果就正常了。参战指的是：死在这波团里，或者从第一次死亡前 15 秒到最后一次死亡之间，和已经参战的敌方英雄交换过伤害（直接或经过别人连起来），且交换时双方都在某个阵亡点 3000 码以内。只按时间窗口、不看地点的版本会把同一时间地图另一头的交火也算进来（审查时发现：夹具第 1 场团把 2 打 2 算成了 4 打 5）。

由 `node scripts/calibrate.mjs <traces 目录>` 生成：

| 团战前的局面（只看两边不相等的团） | 占优一方赢的比例 |
|---|---|
| 参战人数更多 | 74%（132/178） |
| 参战人数多两个及以上 | 72%（28/39） |
| 就绪的大招更多 | 59%（128/216） |
| 就绪的 BKB 更多 | 62%（57/92） |
| 参战者等级之和更高 | 71%（218/306） |
| 当分钟经济领先 | 63%（120/189） |
| **经济落后但参战人数更多** | **78%（31/40）** |

**更正（2026-11-24）**：第一版发布的数字（参战人数 64%、经济落后但人多 24/37）偏低。当时的校准脚本读 trace 时没有像线上那样先关联英雄名。痛苦女王、敌法师等英雄在战斗日志里的名字和 trace 不同，没关联就找不到它们的伤害，参战人数因此算少了。现在脚本和线上读法一致，上表是更正后的数字。结论不变，而且更强。

从这张表能读出两点：

1. 参战人数比经济差更能解释团战胜负（74% 对 63%），而且是另一回事：经济落后的一方只要人到得更齐，40 场里赢了 31 场。"这波输在人没到齐"比"输在经济"更常见，也更可改：玩家能改的是自己当时在哪。
2. 特征必须拿真实结果校准过才能交给模型。43% 那个版本看起来完全合理，交给模型就会被讲成"人多还输，是打法问题"。每个新特征上线前都要过这张表。

样本只有 32 局，比例会随语料增长变化。脚本可以随时重跑，这份文档和 `lib/agent/fightReport.js` 注释里的数字都来自它。

## 3. 路线：四步

### A. 局面层（第一步已实现）

- `packages/review-engine/src/trace/state.js`（纯函数）：
  - `heroStateAt(trace, h, t)`：任意一秒某英雄的状态，包括位置、在做什么、等级、血量、法力、大招、BKB 和 TP 是否就绪。
    - "在做什么"只写录像能证明的：死亡（以及几秒后复活）、在自家基地、正在和敌方英雄交换伤害、正在打敌方建筑。都不是时只给位置。没有兵线数据，所以绝不写"在刷钱"。
    - "就绪"的含义：已学/持有、不在冷却、法力够用。说不清的情况一律给 null，不当成"没好"。
  - `fightParticipation(trace, fight)`：谁参战，以伤害记录为准：从阵亡者出发，沿着阵亡点附近的伤害交换连起来，不靠"离得近"推断。
- `lib/agent/fightReport.js`，两个新工具：
  - `fight_report`：每场团战（编号与 `match_overview` 一致）从玩家一方看：两边各来了几个人、开打时谁的大招和 BKB 好了、每个没参战的人当时在干嘛（死了几秒后复活；或者在哪、离多远、TP 好没好）；另有全局计数。evidence ref 为 `fights:<hero>` 和 `fights:<hero>:<n>`。
  - `game_state`：任意一秒全部十个英雄的状态。ref 为 `state:<hero>:<秒>`。
- 复盘和对话的提示词里新增：
  - 描述团战前先读 `fight_report`。人少输掉的团，先说人在哪，再说怎么打的。
  - 不写"拒绝支援 / 在刷钱"，`tp_ready` 也不当作"来得及"。
  - 人少输掉、而缺的人不是玩家自己的团，归因为团队打法（`team_play`）。
- 提示词版本 22 → 23，旧复盘会按新版本重写。

**实测**：用 DeepSeek 对线上一局（9102822299，幽鬼，58:29 获胜）跑了一次完整复盘。

- 模型主动调用了 `fight_report` 和 `game_state`。
- 写出了"13 场团战你到场 12 场，唯一缺席的 12:15，你人在天辉下路、回城卷轴可用"。
- 在一条发现里引用了 `state:spectre:3160`，说明 52:40 你和三名队友同时阵亡、天辉下路二塔被拆。

同一次复盘也暴露了一个已有的校验漏洞：模型把距离 11112 写成了 11300，校验没拦住。原因是正文里的数字只要和任何一个工具输出的某个数相差 0.5% 以内就算过关，这里撞上了 `farm_report` 里的 11297。新工具带来大量四五位数的距离，会让这种碰撞更常见，已单独开 issue（#295）。

### B. 因果层：每种结果都有校准过的解释

团战只是第一种结果。下一步把同样的方法用到：

- **塔和兵营（已实现：`siege_report`）**：把每次推塔都找出来，即敌方英雄对同一座建筑造成伤害、两次伤害间隔不超过 30 秒、合计至少 3 个"英雄·秒"。对每次推塔记录：
  - 谁在打；
  - 守方谁在附近（在某个打塔英雄出手的那一秒，离他 1800 码内）；
  - 其余每个人在干嘛、离多远、TP 好没好；
  - 塔掉没掉。

  32 局共 716 次推塔（同一英雄同一秒的普攻和技能只算一次）：

  | 打塔人数减去守方在附近人数 | 塔被拆的比例 |
  |---|---|
  | −1 及以下 | 66%（73/111） |
  | 0 | 55%（68/123） |
  | 1 | 71%（153/217） |
  | 2 | 90%（119/132） |
  | 3 及以上 | 96%（128/133） |

  多出两个人以上，塔几乎一定掉（93%，247/265）；守方能凑到差一个以内，掉塔率降到 65%。推塔开始时守方死了 4 个以上，88% 会掉。所以"塔为什么掉"首先是人数和人在哪的问题。对应提示词：讲建筑得失之前先读 `siege_report`；"在附近"不等于"在守"。

  **探针查出的一处错（已改）**：`siege_report` 里"推塔方其余""守方不在附近"这两组英雄的位置，取的是推进**开始**那一秒，工具说明却写成"建筑倒下时队伍在哪"。一次推进可以打一分钟，这两个时刻的位置不是一回事。两步探针问"我方丢第一座塔时我在哪"，对话 agent 照工具给的说，就答错了：9080127650 里推进 16:11 开始时玩家在天辉中路，16:44 塔倒时已经在夜魇中路；9101152780 里是夜魇上路和河道上路。现在工具说明、`rule`、两处提示词都写明这两组位置是推进开始时的；玩家自己一方的建筑倒下时，另给 `me_when_it_fell`，即倒下那一秒玩家的位置（阵亡则给复活时间，没有采样则是未知）；其他人在那一秒的位置用 `game_state` 查。证据卡片上也标了"推进开始时"，并单列"被拆时你在哪"。改完之后对话 agent 这类题答对多少，要等重跑探针才知道，还没有跑。
- **经济窗口**（`window_report` 已有）：窗口期内双方的局面，比如领先方是否把人数优势转成了建筑。
- **死亡（已实现：`death_context` 增强）**：每次阵亡新增两项：
  - `traded_within_15s`：15 秒内对面是否也死了英雄；
  - `allies_elsewhere`：不在 2200 码内的队友当时在干嘛、在哪、离多远、TP 好没好，或者还要几秒复活。

  汇总里新增"换到了 / 没换到 / 身边没人且没换到"三个列表。

  32 局的校准结果推翻了一个常见说法。"一个人站位危险"在数据里不成立：每 5 秒取一次所有活着的英雄，看 20 秒内死没死。

  | 位置 | 身边（2200 码）队友 | 20 秒内阵亡 |
  |---|---|---|
  | 敌方半场 | 0 | 5.7%（403/7078） |
  | 敌方半场 | 2 个及以上 | 7.1%（1578/22096） |
  | 己方半场或河道 | 0 | 4.0%（1494/37204） |
  | 己方半场或河道 | 2 个及以上 | 8.5%（2661/31320） |

  抱团的人参与的团战多，单位时间里反而死得更多。真正的区别在于死了之后换没换到：

  | 阵亡时身边（2200 码）队友 | 15 秒内对面也死了英雄 |
  |---|---|
  | 0 | 31%（187/594） |
  | 1 | 48%（420/868） |
  | 2 个及以上 | 72%（818/1136） |

  所以复盘该说的不是"一个人危险"，而是"一个人死，大多数时候什么也没换到"。提示词按这个改了：用这局"身边没人且没换到"的次数来说，不说"单独站位本身危险"。

每个解释都附语料基准率，让模型知道这个因素平常有多重要，不至于把一次巧合讲成规律。

#### 一个会误导的计数：“至多只伤到一名敌方英雄的施放”

`ability_audit` 给每个技能数几种“没放好”的施放，规则可以按这些计数在下一局录像里核对（`counted_by`）。其中一种原来的定义是：没有英雄目标、伤害只打到一名敌方英雄或一个都没打到。读一局干扰者的数据时发现它把好的施放也算了进去：5 次“只打到一人”的静态风暴里有 4 次把那个人杀了。

在语料 32 局的大招上数了一遍（2026-11-25），这个计数共 2001 次：

| 实际是什么 | 次数 |
|---|---|
| 1300 码内没有敌方英雄、也没伤到任何人（赶路、打钱、埋雷） | 1010（50%） |
| 被它伤到的敌方英雄 12 秒内阵亡（单杀） | 348（17%） |
| 在敌方英雄附近放出、至多伤到一人、被伤到的人都没死 | 643（32%） |

只有最后一类是“没放好”。天怒法师的神秘之耀 63 次里 42 次是单杀；示例局里兽王的野性之斧 98 次施放被算了 90 次，其中 60 次身边根本没有敌人。

现在的定义就是最后一类（`no_hero_target_near_enemies_at_most_one_damaged_and_none_died`），习惯 `reached_few` 按它计数，页面和提示词的说法也跟着改了。“死的是不是被它伤到的那个人”要对上：别人在别处杀了人不算单杀。已经设成目标的旧规则，下一局会按新口径数，数字只会比旧口径小。

### C. 判断层：决策点

教练教的是"那一刻该怎么选"。需要一个 `decision_points` 工具，从局面里找出有选择的时刻：

- 塔刚倒；
- 赢团之后（推进还是撤退）；
- 敌方核心出了关键大件；
- 我方大招全部就绪；
- 敌方关键人物死亡（有多少秒的窗口）。

对每个时刻，列出这局实际怎么选的，以及语料里同类局面下不同选择的后果分布。模型再从这些事实出发给判断，而不是凭记忆。

**第一种已实现：赢团之后（`decision_points`）**。对每场分出胜负的团战，记录：

- 输的一方在最后一次阵亡 10 秒后还有几个人没复活、各自还要几秒；
- 赢的一方接下来做了什么，分四种：
  - 拆到建筑：从团战开始到结束后 120 秒内，对方有建筑倒下，不管最后一击是谁打的；
  - 打了肉山；
  - 推了没拆掉；
  - 什么都没拿。

"拆到建筑"的口径和 `tempo_report` 的"团后拆到建筑"完全一致，两个工具不会互相矛盾，测试里锁定了这一点。

32 局、321 场分出胜负的团战：

| 团后 10 秒对面仍未复活 | 场数 | 拆到建筑 | 打肉山 | 推了没拆掉 | 什么都没拿 |
|---|---|---|---|---|---|
| 0–1 人 | 26 | 4 | 0 | 4 | 18 |
| 2 人 | 84 | 31 | 3 | 8 | 42 |
| 3 人 | 115 | 59 | 1 | 13 | 42 |
| 4 人及以上 | 96 | 58 | 2 | 12 | 24 |

即使对面死了 4 个以上，仍有四分之一的团战什么都没换到。这是最直接的"赢了团却没赢比赛"，也是复盘最该指出的地方。工具只说"没拿到"，不说"什么都没做"，因为没有兵线数据，打钱和带线看不见。

**第二种已实现：塔刚倒（`decision_points` 的 `after_a_tower_fell`）**。对每座被对方拆掉的一到三塔（反补的不算），记录：

- 拆塔方接下来 120 秒做了什么：又拆了建筑、打了肉山、推了没拆掉，或什么都没拿；
- 同一时间拆塔方自己有没有掉建筑（换塔）；
- 这座塔是不是某场赢团的后续；
- 玩家当时在哪：在打这座塔、在附近（离打塔的人 1800 码内）、阵亡中，或在别处（给出区域和距离）。

32 局、379 座塔：

| 塔 | 之前有没有赢团 | 座数 | 又拆了建筑 | 打肉山 | 推了没拆掉 | 什么都没拿 | 同时自己掉了建筑 |
|---|---|---|---|---|---|---|---|
| 一塔 | 有 | 52 | 18 | 1 | 5 | 28 | 8 |
| 一塔 | 没有 | 108 | 27 | 2 | 11 | 68 | 34 |
| 二塔 | 有 | 61 | 35 | 3 | 8 | 15 | 4 |
| 二塔 | 没有 | 68 | 24 | 3 | 7 | 34 | 16 |
| 三塔 | 有 | 55 | 51 | 0 | 0 | 4 | 1 |
| 三塔 | 没有 | 35 | 31 | 0 | 0 | 4 | 3 |

- 拆一塔之后什么都没拿是常态（60%）；没有赢团的一塔有将近三分之一是换塔。所以拆一塔后没拿到东西不值得单独批评。
- 二塔是分水岭：赢团后拆二塔，过半会接着拆下一座；没有赢团就拆二塔，一半什么都没拿。
- 三塔倒了，下一座建筑几乎一定倒（91%）。

对"玩家在别处"，提示词要求只说他在哪、掉了什么，不说他该不该去。他可能在另一路拆塔或打钱，判断要看全图。

**第三种已实现：刚出大件后的团战（`fight_after_a_big_item`）**。"大件"沿用教练已有的口径（`power_spikes`、`window_report` 用的同一条规则）：按这局所在版本的价格，2000 金以上、由配方合成的装备，或者跳刀、BKB 这类关键装备。每场在某个英雄刚拿到大件后 120 秒内开打的团战，列出双方这段时间出的大件和谁少死人。

32 局里，开打前 120 秒内只有一方出了大件、且分出胜负的团战：

| 情况 | 出大件一方少死 |
|---|---|
| 全部 | 60%（62/103） |
| 出大件一方经济领先 | 71%（24/34） |
| 出大件一方经济落后 | 44%（11/25） |
| 对照：前 120 秒没人出大件，经济领先一方 | 58%（22/38） |

最初用"4000 金以上"做口径时，落后方刚出大件的胜率看起来高于常态（56%）。换成教练的口径后，这个差别没有了：落后方刚出大件，赢的比例和平常落后方差不多（44% 对 42%）。大件主要是"经济领先"的标志，不是单独赢团的原因。提示词按这个写：可以说"对面刚出 BKB 时我们接了团"，但不能说"BKB 让他们赢了这波"。有经济数据的场次只有 59 场，样本还小。团战从第一次交手算起，不是从第一次阵亡算起：交手开始后才出的装备不算"带着大件接团"。

**"我方大招全部就绪"校准后不做成决策点**。每 5 秒检查一次：某一方活着的英雄里就绪的大招比对面多 2 个以上（自己至少活 4 人），记下这种局面出现的时刻，同一方一分钟内最多记一次。32 局共 436 次。其中 155 次在 90 秒内开打（从第一次交手算起，不是从第一次阵亡算起）：这一方少死 73 次，多死 62 次，持平 20 次，分出胜负的只赢了 54%，和抛硬币差不多。团战开始时参战者大招多 2 个以上的一方，少死的比例也只有 62%（45/72），而人数多的一方是 74%。

所以"大招都好了却没打"不是语料支持的判断。做成决策点只会让模型高估它。提示词改成：不能只用大招就绪来解释一场团战，也不能说"大招都在就该打"。要看的是谁把大招交给了谁（`ability_audit`）。`calibrate.mjs` 保留这一节，语料变大后可以重看。


**第四种已实现：敌方关键人物死亡**。这一种没有单独做成新的决策点类型。被单杀的一次也算"赢团"（1 换 0），所以它已经在赢团决策点里了。现在每个赢团点多一项 `losers_richest`：

- 团战开始那一分钟，输的一方谁的经济最高。口径和 `farm_report` 一样：优先用比赛数据的每分钟金钱，没有就用录像里的每分钟身价，两种不混用；
- 团后 10 秒他是否还没复活，还要几秒。

并列最高时不算任何人是"经济最高"。没有逐分钟金钱数据的比赛，这一项不出现，按未知处理，不当成"活着"。

32 局里有身价数据的 17 局，团后 10 秒对面还有 3 人以上没复活的赢团：

| 对面经济最高的英雄 | 场数 | 拆到建筑 | 什么都没拿 |
|---|---|---|---|
| 在其中，30 秒以上才复活 | 60 | 38（63%） | 15 |
| 在其中，不到 30 秒复活 | 16 | 6 | 7 |
| 活着 | 51 | 20（39%） | 24 |

同样是死了 3 个以上，对面核心也死了、而且 30 秒以上回不来时，拆到建筑的比例从 39% 升到 63%。这种窗口浪费掉，是最该指出的。提示词按这个写，汇总里也有我方"赢团后对方经济最高者 30 秒以上未复活"的场数和结果。

决策层的四种已经做完（大招就绪那一种校准后没有做成决策点）。接下来是 D 层：衡量。

#### 转折团：输掉的一局是从哪场团战开始输的

`match_overview` 对输掉的一局给出 `turning_fight`（`packages/review-engine/src/trace/turningFight.js`）。只看己方阵亡更多、开打时经济差还不低于 -2000 的团战：

1. 如果其中有一场打完两分钟内比赛就结束了，就是它——开打时还有得打，打完基地没了，之前的团战都没有把比赛打死；
2. 否则取开打到结束后两分钟经济差跌得最多的那场，跌幅要超过 1500。

页面团战条上的"转折"标的就是这一场（页面不再自己算一遍）。

为什么要有它：评分表要求复盘讲到转折团，而基线里做到的只有三分之一——模型习惯从计数器往上拼发现（落单的死亡、晚出的装备、捏着大招死），页面标出的转折团反而没人分析。现在提示词要求先读这一场；校验发现没有任何一条发现落在这场团战上时，在修正轮里提一次（只是提醒，不删任何东西：玩家不在场时，写进 `your_part` 就算回答了；`fight_report` 已经说玩家不在这场团战里的，不提）。

### D. 衡量层：理解基准

不衡量就谈不上"提升"。分三级：

1. **确定性探针**：从录像能算出标准答案的问题，比如"25:10 我方谁不在团里、在哪"。对话 agent 自动问一遍，检查回答是否与工具一致。可以全自动，进 CI 或定时任务。
2. **校准表**（`scripts/calibrate.mjs`：团战、推塔、阵亡、肉山、假眼）：每加一个局面特征，先看它对结果的解释力，再交给模型。数据刷新定时任务可以每周用新解析的录像重跑一次。**快照和比对已实现**：最近一次的结果存在 `data/calibration.v1.json`，`scripts/calibrate-diff.mjs new.json` 把新一轮和它逐行比对。每张表的每一行按"总数 + 各结果的次数"读，比例变化超过抽样误差（双比例 z ≥ 2，两边都至少 20 例）才列出来，退出码 1。新旧语料是重叠的，所以 z 只是提示该回头看哪个数，不算检验。2026-11-25 用线上 34 局（27 局带假眼）重跑，和这份文档引用的 32 局比：95 个比例都没有超出误差（含拿盾后盾的用掉、过期比例，和大招优势一方在分出胜负的团战里的胜率），21 个样本太少不判（大多是假眼那几行，旧的 32 局里它们是 0 例）。所以下面各表仍是 32 局的数字。新的 34 局里，假眼的关键数也没变：在己方半场单人站在敌方假眼下，20 秒内阵亡 9.9%，没有假眼 3.3%（25 局时是 10.2% 和 3.2%）。定时跑还差一步：录像 trace 在私有 GCS 桶里，GitHub Actions 没有 GCP 凭据。
3. **专家标注**（#164）：高分玩家和教练标注"这局真正的问题是什么"，用来衡量复盘的命中率。这是唯一能衡量"判断"的方式，也是最慢的一级，应尽早开始积累。

#### 两步的探针

第一级很快测饱和，所以加了三类要两步才答得出的题：先从一个工具拿到时刻，再到另一个工具查答案。

| 问题 | 两步 |
|---|---|
| X 开打的那波我们赢了，之后两分钟拆了几座建筑 | 问的是开打时间（`fight_report`、`match_overview` 给的），`decision_points` 的 `clock` 却是这波结束的时间，要按 fight 编号对上 |
| 我方丢第一座塔时我在哪 | `match_overview` 拿时间，`game_state` 在那一秒查位置 |
| 第一个盾之后五分钟，拿盾一方拆了几座建筑 | `roshan_report` 找到第一块盾，再数它后面的建筑 |

一步的题几乎全对，两步的题 en 降到 97%。错的都是位置：答案里写的是另一个工具、另一个时刻的位置，或者把"自家/敌方"换算错了。数建筑的两步题全对，说明对上 fight 编号这一步模型做得到。

建筑数的判分只看答案里第一句带数量的话。后一个数和前一个数之间有"和""、"或逗号，没有冒号、破折号、"其中"这类把总数隔开的词，动手的一方也没有换，它就是分项，加起来算（"拆了两座二塔，还拆了一座三塔"是三座）；中间夹着的塔的级别、时间、括号里的补充都不影响。换了动手的一方，后面的数就不加，前面已经加上的分项仍然算数（"你们拆了两座，对面拆了一座"是两座；"我们拆了两座塔和一座兵营，对面拆了一座塔"是三座）；说建筑是谁的不算换人（"两座敌方塔和一座敌方兵营"是三座），同一方再说一遍也不算（"……我们又拆了一座兵营"）；第一个数数的是笼统的"建筑"、后面的数都点明了是塔还是兵营，或者它后面跟着冒号、破折号、"其中"，它就是总数（"3 座，2 座塔、1 座兵营"是三座）；数字碰巧相等不算依据（"两座塔、一座近战兵营和一座远程兵营"是四座）。时间窗口里的"两分钟""五分钟"、塔的级别"一塔""tier 1"都不算数量。战斗还没结束时倒下的建筑不算"之后"拆的。"那时你已阵亡"同样看答案先说的那一句，后面建议里的"你活着站在塔后"不算。

判分也跟着改了：玩家会说"你自家中路""下路河道"，不会照抄地名表。`placesIn` 按玩家的说法读地点："你/自家"是玩家这一方，"敌方/对面"是另一方。只有阵营、路、野区与否都对上才算答对。这样"Radiant mid"答"夜魇中路"仍然判错。中文"一座"现在算数量。

这些判分规则是在跑完之后、对着存下来的答案一轮轮改出来的，每改一次都用 `--regrade` 重新判分，上面两张表的分数都没有变。只有最后一处（分项之间夹着塔的级别时也要相加）没能重判：存答案的目录是临时的，已经不在了，这一处只有单元测试。下次重跑时把 `--out` 的结果放到留得住的地方，改判分才能继续不花模型费用地复核。机械判分读的是自然语言，判"通过"的答案不保证句句都对；每一条判"未通过"的答案都人工读过。数建筑这一类最难判：答案可以先给总数再列分项，也可以只列分项，还可以把双方的数写在一句里，规则只能覆盖常见的写法。要判得更稳，下一轮可以在问题里要求"先给出数字"，判分只读开头那个数。

#### 探针花的是线上的账户

本机 `.env` 里的 DeepSeek key 和线上的 key 不是同一把，扣的却是同一个账户：两把 key 查到的余额分毫不差。2026-11-25 这几轮探针（合计约 2200 万输入 token）跑的过程中，余额见了底；这个账户线上和别的脚本也在用，探针是这段时间里已知最大的一笔开销。03:50 UTC 前后探针开始收到 402；04:11 线上有一位用户对自己的比赛连续两次请求复盘，都在开始后一秒左右失败，充值之后才恢复。跑之前没有查这把 key 扣的是哪个账户、还剩多少。

现在 `scripts/probe-chat.mjs` 开跑前先读账户余额（`lib/agent/modelBalance.js`），之后每发出 20 题再读一次（失败的调用也算，查余额期间不发新题）。余额低于 `--min-balance`（默认 50，账户的币种）或者读不到余额，就不开始或者立刻停下，退出码 4；供应商一旦回 402 也立刻停。没问到的题记为 `not_asked`，调用失败的记为 `error`，都不算答错，不进分母。跑完会报这一轮实际花了多少。`--no-balance-check` 只给没有别的东西依赖的账户用。

#### 复盘评测：第一步已实现

探针测的是对话 agent 读工具准不准，校准表测的是特征有没有解释力。复盘本身说得对不对、读不读得下去、同一局重跑一不一致，之前没有东西测。`lib/agent/evalReview.js` 和 `scripts/eval-review.mjs` 不调模型，直接给已存的复盘打分：

| 测什么 | 怎么测 |
|---|---|
| 读起来怎样 | 结论字数；正文（结论、发现、规则、改法）里带 3 个及以上时间或数字的句子占比；中文复盘里漏出的英文词 |
| 讲不讲得通 | 每条规则在这局出现过几次（不到 2 次算单薄）；规则自己写着"只有 1 次"；同一份复盘里既说对位占优又说劣势对位 |
| 说没说到点上 | 只对有评分表的局（`evals/reviews/<比赛>.<英雄>.json`）：必须讲到的点讲到没有，不能说的话说了没有，有没有一条发现落在转折团上，主因是否在评分表接受的范围内 |
| 稳不稳定 | 同一局（同英雄、同语言）有三份以上复盘时：主因一致的比例，首条发现引用的记录重合多少 |

评分表是人对一局比赛的判断，写成可以机械核对的形式：每个要点给出它落在哪些记录或时间上（`any.refs`、`any.clocks`），以及发现里必须出现的词。草稿（`status: draft`）和校对过的（`approved`）分开统计。

**重新生成再打分**（`scripts/eval-run.mjs`，要花钱）。给已存的复盘打分不花钱，但改了提示词或工具之后，要知道复盘变好还是变差，只能让同一批比赛在改之前和改之后各重写几份：

```bash
# 在 main 上
node scripts/eval-run.mjs --traces <trace 目录> --matches <比赛记录目录> --out runs/before --runs 3
node scripts/eval-review.mjs runs/before --json before.json
# 在改动的分支上
node scripts/eval-run.mjs --traces <trace 目录> --matches <比赛记录目录> --out runs/after --runs 3
node scripts/eval-review.mjs runs/after --baseline before.json
```

默认重写每份评分表对应的那局（`--games` 可以另指）。`--matches` 给每局的比赛记录（OpenDota 的 JSON），线上生成复盘时也带着它；不给就只凭录像，开跑前的清单会写明每局是哪种。写出的文件名是存量复盘的名字加 `.r<n>`，打分脚本把同一版本的几份都算进去，三份以上就有稳定性数字。

花的是线上同一个 DeepSeek 账户的钱（2026-11-25 一次探针把余额跑空，一位访客的复盘因此失败），所以它这样约束自己（`lib/agent/evalRun.js`）：

| 什么时候 | 做什么 |
|---|---|
| 开跑前 | 打印要写几份、预计花多少（每份按 0.25 估，实测 0.16）、预算、余额、保留线。余额读不到不跑；预计超出预算（`--budget`，默认 5）不跑；跑完会低于保留线（`--floor`，默认 50）不跑 |
| 每写完一份 | 再读一次余额。低于保留线、账户已经少掉的钱达到预算、或者余额读不到了，就停，并列出没跑的 |
| 始终 | 一次只写一份，不并行 |

`--dry-run` 只打印清单和余额。设了 `EVAL_DEEPSEEK_API_KEY` 就用它（评测单独的账户），否则用 `DEEPSEEK_API_KEY` 并明说这是线上的账户。

还没做的：评分表从 4 局扩到 12–15 局（先要工具能读辅助的事）；用模型判断语义是否命中（现在只按记录、时间和词核对，会漏掉换了说法的命中）。

#### 读者怎么说：每条发现下的三个按钮

评分表是我们对一打比赛的判断；复盘说得对不对，只有打那一局的人知道。页面在每条发现下面问一句"这条说得对吗？"，三个回答：说得对、不对、没用。后两个会再问一句原因，也是固定选项：

| 回答 | 原因 |
|---|---|
| 不对 | 事实不对（`fact`）；事实对，结论不对（`judgment`）；这不是我能改的（`not_mine`） |
| 没用 | 我早就知道（`knew`）；太笼统，不知道怎么做（`vague`）；不是这局的关键（`minor`） |

存什么（`lib/agent/feedback.js`，`POST /api/agent/:matchId/feedback`）：比赛、英雄、语言、提示词版本、模型；是第几条发现，它的标题和引用的记录（从存着的那份复盘里抄，不信请求里写的）；回答和原因。不存什么：读者打的任何字（没有输入框）、地址、账号、浏览器标识。同一个读者对同一条发现改主意，新的回答覆盖旧的那条，不会多出一条。只收对"现在存着的那份复盘里、这个位置上的这条发现"的回答：页面把它显示的那份复盘的提示词版本和撰写模型的 id（不是"默认模型"，默认会换）一起发回来，版本对不上或标题对不上的，不收，也不会记到新版本头上。浏览器记住"说过什么"时用的也是这几样，所以复盘重写之后同一个位置会重新问。

记录在 `agent/feedback/` 下，一条一个对象。看汇总：

```bash
gcloud storage cp -r 'gs://<agent 桶>/agent/feedback' <目录>
node scripts/feedback-report.mjs <目录>/feedback
```

输出按提示词版本分行的"说得对"比例、首条发现（页面拿它当这局的一课）单独一行、各原因的次数，以及最近的"不对 / 没用"列表。没人回答的版本没有比例，不是 0%。

"不对：事实不对"的那几条值得逐条看：那是校验放过去的错。"没用：不是这局的关键"多了，说明发现的排序有问题。

## 4. 不变的原则

- 每个数字都来自工具，模型不能自己算。evidence ref 可以复算，读者能自己核对。
- 未知就是 null，不当成"没有"。新工具的 `gaps` 写明了视野、兵线、买活不知道，也写明了肉山只能从拿盾看出来。
- 判断留给模型，工具只给事实。"没参战"是事实，"应该去"是判断。
